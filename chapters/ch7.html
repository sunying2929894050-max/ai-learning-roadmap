评估：怎么知道它真的有效

LLM 输出不确定、开放式，没法像传统软件那样"== 期望值"判对错。评估是区分 AI 工程师和调包玩家的分水岭——用度量代替"我觉得还行"。本章把 ch1 的概率采样、ch3 的 prompt 设计、ch4 的成本、ch5 的 RAG 忠实度全部变成可测量的指标。

⬡

改了 prompt 就上线，然后呢？

😬 真实场景

你把文档助手的 system prompt 从 v1 改成了 v2，在三个例子上跑了一下："嗯，回答好像更简洁了，感觉不错。"然后你上线了。

一周后，用户开始抱怨：助手在某类问题上开始捏造答案，但你没发现，因为你只测了你脑子里想到的那三个例子。那三个例子确实变好了——但还有二十个场景，你从来没测过。

→ 核心问题：你怎么"知道"这次改动是变好了而不是变差了？
主观感受不是答案。三个例子不是答案。可重复运行的评估集才是答案。
传统软件测试 vs LLM 评估
传统单元测试：assert result == "expected"——输入固定，输出唯一，对错非黑即白。LLM 测试呢？同样的 prompt，每次输出不同；同一问题有十个都"正确"的回答方式。== 永远不会通过，但答案可能是对的。这就是为什么 LLM 评估是一个独立的学科，而不是"把单元测试拷贝过来"。
◈

为什么 LLM 评估难

在理解"怎么评估"之前，先要理解"为什么评估是个难题"——根源在 LLM 本身的两个结构性特征。

速览：两大原因让 LLM 评估不同于传统测试
🎲 不确定性
同样的输入，每次输出不同。不能用"== 期望字符串"判断。
📖 开放性
一个问题有多个"正确"答案，精确字符串匹配会把对的答案判成错的。
举例
问：年假有多少天？
答1：入职满一年员工每年享有10天带薪年假。✓
答2：满一年可以休10天年假。✓
答3：10天，满三年升到15天，满五年20天。✓
三个回答都正确，字符串却完全不同。精确匹配只能通过答1（如果恰好被设为参照），2和3都会被判错。
从 ch1/ch2 的底层机制理解不确定性的来源

回扣 ch1 四大核心概念 和 ch2 Token 分词：大语言模型在推理时并不是"找到正确答案"，而是在每个位置从一个概率分布上采样下一个 token。采样（Sampling）本身带有随机性——即使是同样的输入，因为 temperature > 0，每次采样得到的 token 序列都可能不同。

为什么这使评估变难？
• 同一个"有效的"系统，在评估集上的表现会随机波动。你需要多次采样或固定随机种子（temperature=0）来得到可重复的结果。
• 即使 temperature=0（贪心解码），不同版本的模型、不同 API 供应商的实现可能仍有输出差异。
• 对于开放式任务，追求"每次输出一模一样"本身是错误目标——应该追求"每次输出都满足质量标准"。

开放性的本质：正确答案是一个集合，不是一个字符串
传统软件测试的心智模型：函数 f(x) 有唯一正确输出 y。LLM 的心智模型：函数 f(x) 有一个"可接受输出集合" S，|S| 可能是无限大的。评估的任务是判断"输出 y 是否在集合 S 里"，而不是"y == y_expected"。

这个转变让评估变成了一个语义理解问题，不再是字符串匹配问题。语义理解意味着需要用人或另一个 LLM 来做判断——这正是 LLM-as-judge 存在的原因。
HELM 基准：Holistic Evaluation of Language Models（斯坦福） MT-Bench：用 GPT-4 做评判的对话评测框架
🔍

评估的几种方式

没有一种方式完美，工程实践中通常组合使用。从确定性最高到主观性最高，依次是：精确匹配 → 相似度指标 → 任务专用指标 → LLM-as-judge → 人工评估。

速览：四种主要评估方式对比
方式适合场景优点缺点
精确匹配结构化输出（JSON、分类、是/否）完全自动、可靠只适合有唯一答案的场景
相似度指标摘要、翻译（ROUGE/BERTScore）自动化、有参照相关性低时误导性强
任务专用指标RAG（忠实度）/ Agent（完成率）针对性强需要为每个任务设计
LLM-as-judge开放式问答、写作扩展性好、可定制 rubric评判模型本身有偏见
四种方式的深层机制与前几章回扣

① 任务专用指标：RAG 忠实度（回扣 ch5）
回扣 ch5 完整管线与失败模式：RAG 最常见的失败是"检索命中但模型无视上下文，用参数记忆凑了个答案"——这就是忠实度（Faithfulness）问题。忠实度评估：给定<上下文, 问题, 答案>，判断"答案里的每个事实声明是否能从上下文里找到依据"。另一个指标是检索准确率（Precision@k）和召回率（Recall@k）：正确答案出现在 top-k 检索结果里的比例。

② 任务专用指标：Agent 评估（回扣 ch4/ch6）
回扣 ch6 Agent 循环：Agent 的质量不只看最终答案，还要看：工具调用准确率（调了对的工具吗）、步数效率（用了几步）、成本（回扣 ch4 token 成本：步数越多成本越高）。一个5步完成的任务和一个3步完成的任务，如果准确率相同，后者更优。

③ LLM-as-judge：评判本身是一次 prompt 工程任务（回扣 ch3）
回扣 ch3 Prompt 是什么：LLM-as-judge 的核心是给评判模型一个评分标准（rubric），让它按照 rubric 逐条打分并给出理由。rubric 的质量决定评判的质量——这和 few-shot prompt 设计是同一件事：给模型清晰的任务描述和期望格式。一个好的 rubric 能区分"答案是否基于上下文""是否完整""是否简洁"；一个差的 rubric 只说"给个1-10分"——模型会按自己的理解随机打分。

④ 评估评估者：判官也有幻觉（回扣 ch1）
回扣 ch1 AI 的风险：LLM-as-judge 里的评判模型自己也是一个 LLM，同样有 ch1 讲过的幻觉和偏见。已知的系统性偏见：
• 位置偏见：同样两个答案，放在"选项A"比"选项B"更容易被选中
• 啰嗦偏见：更长的答案往往被打更高分，即使长度是冗余的
• 自我偏好：GPT-4 评判时偏爱 GPT-4 风格的回答；Claude 评判时偏爱 Claude 风格

解法：多个评判模型交叉验证；用人工评估抽样校准 LLM-judge 的准确率；在 rubric 里明确"不考虑答案长度，只看内容质量"。

⑤ 人工评估：金标准但不可扩展
人工评估的评分者间一致性（Inter-Annotator Agreement, IAA）是衡量评估本身可靠性的关键——如果两个人评同一条输出的结论差异很大，说明评分标准不清晰，即使是人工评估也不可信。
RAGAS：RAG 专用评估框架（忠实度 + 答案相关性 + 上下文相关性） MT-Bench / Chatbot Arena：LLM-as-judge 的实证研究
◇

建评估集：工程师 vs 调包玩家的分界线

评估集（Eval Set / Test Set）是一批"问题 + 期望行为"的样本。每次改动（换 prompt、换模型、改切块策略）都跑一遍评估集，看指标有没有退步——这叫回归测试。没有评估集，你就是在盲飞。

速览：一个最小可用评估集的构成
①
核心场景覆盖（20-50条）

覆盖系统实际会遇到的主要问题类型。比如文档助手：年假类、报销类、绩效类、边界情况（问题不在文档里）。

②
失败案例（10-20条）

你已知系统容易出错的场景。把这些专门列出来，确保每次改动都不会让它们变更差。

③
期望行为标注（不必是唯一答案）

可以是关键词（答案里必须包含"10天"）、期望态度（如果找不到答案，应说"未找到"而不是编造）、或 rubric 描述。

评估集的大小与代表性：小心"评估错觉"

评估集太小是最常见的陷阱。如果你只有10条评估数据：
• 一次偶然的好输出让准确率从70%→80%（只是1条结果改变了）
• 你在开发集上过拟合——无意识地优化了这10条，但其他场景退步了
• 统计上，10条数据的置信区间很宽，指标差3-5%完全在统计噪声范围内

"工程师 vs 调包玩家"的核心差异：
调包玩家的工作流：改 → 试几个例子 → 看起来还行 → 上线
AI 工程师的工作流：改 → 跑评估集（100+条）→ 所有指标都没退步 → 上线

这两个工作流在小项目上差异不大，在生产系统上差异是灾难性的。LLM 输出有长尾分布——最常见的输入通常表现好，边界情况才是问题所在。"看几个例子"永远看不到长尾。

评估集不是一次性的
生产中发现了新的失败案例？加进评估集。用户反馈了新的问题类型？加进评估集。评估集应该随系统迭代而增长，不是只在项目开始时建一次。这就是为什么 ch7 在整个课程接近末尾——你需要先用了系统，才知道哪些是代表性的边界情况。

离线评估 vs 在线评估

评估不只发生在上线前。完整的评估体系是两段的：上线前的离线评估（跑评估集）+ 上线后的在线评估（监控真实用户行为）。两者互补，缺一不可。

速览：两类评估的角色
🧪 离线评估（上线前）
跑预先准备的评估集。快速、可重复、可对比版本。是"不上线的防线"。每次改动都跑一遍。
📡 在线评估（上线后）
监控真实用户的输入和反馈。发现离线评估集没有覆盖的真实分布。是"上线后的听诊器"。
为什么两类评估都不可少

只做离线评估的问题：
评估集是你预先构造的，代表你能想到的场景。真实用户的输入分布往往和你的想象差距很大——方言、错别字、多语言混用、完全超出预期的问题类型。再好的离线评估集也无法覆盖真实世界的长尾。

只做在线评估的问题：
上线才发现问题，代价太高。一个有明显 bug 的 prompt 变更会影响真实用户，你无法快速回滚，因为你没有事先测量基线。

A/B 测试：在线评估的最严格形式
A/B 测试将用户随机分成两组，A组用旧版本，B组用新版本，对比关键指标（用户满意度、任务完成率、平均评分）。A/B 的优点：真实用户、真实行为、有统计显著性保证。缺点：慢（需要足够流量才有统计意义）、成本高、新版本如果很差会损害一部分用户体验。

在线监控的最小配置：
• 在输出旁加👍/👎按钮（最简单的用户反馈）
• 记录用户是否追问（"你说的不对"通常意味着上一条回答有问题）
• 监控"模型说找不到信息"的比例（RAG 未命中率）
• 监控平均步数和成本（Agent 任务）

def judge_answer(question: str, context: str, answer: str) -> dict:
    prompt = (JUDGE_PROMPT
              .replace("{question}", question)
              .replace("{context}", context)
              .replace("{answer}", answer))
    resp = ds.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "user", "content": prompt}],
        max_tokens=512,
    )
    raw = resp.choices[0].message.content
    total = None
    for line in raw.splitlines():
        if line.startswith("总分"):
            try:
                total = int(line.split("：")[1].split("/")[0].strip())
            except (IndexError, ValueError):
                pass
    return {"raw": raw, "total_score": total}

# ── LLM-as-judge：带 rubric 的评判调用 ─────────────────────────────
JUDGE_PROMPT = """你是一个严格的 AI 系统评判员。请根据以下 rubric 对给定的问答进行评分。

【问题】{question}
【参考上下文（RAG 检索到的内容）】{context}
【待评判的回答】{answer}

【评分标准（Rubric）】
1. 忠实度（0-3分）：答案中的事实是否全部来自上下文？是否有凭空捏造？
2. 完整性（0-3分）：答案是否回答了问题的所有要点？
3. 相关性（0-2分）：答案是否直接回答了问题，没有跑题？
4. 简洁性（0-2分）：答案是否简洁，没有不必要的冗余？

请逐条评分并给出理由，然后给出总分（0-10）。

输出格式（严格遵守）：
忠实度：X/3 — 理由
完整性：X/3 — 理由
相关性：X/2 — 理由
简洁性：X/2 — 理由
总分：X/10
总结：一句话说明主要问题或亮点"""


def judge_answer(question: str, context: str, answer: str) -> dict:
    """用 LLM-as-judge 评判一个回答，返回结构化评分。"""
    prompt = (JUDGE_PROMPT
              .replace("{question}", question)
              .replace("{context}", context)
              .replace("{answer}", answer))
    resp = ds.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "user", "content": prompt}],
        max_tokens=512,
    )
    raw = resp.choices[0].message.content
    # 简单提取总分
    total = None
    for line in raw.splitlines():
        if line.startswith("总分"):
            try:
                total = int(line.split("：")[1].split("/")[0].strip())
            except (IndexError, ValueError):
                pass
    return {"raw": raw, "total_score": total}


# ── 忠实度快速检查（关键词匹配版，不消耗 LLM） ─────────────────────
def keyword_check(answer: str, keywords: list[str]) -> dict:
    found = [kw for kw in keywords if kw in answer]
    missing = [kw for kw in keywords if kw not in answer]
    return {
        "found": found,
        "missing": missing,
        "keyword_hit_rate": len(found) / len(keywords) if keywords else 1.0,
    }


# ── 主评估循环 ──────────────────────────────────────────────────────
def run_eval(use_llm_judge: bool = True) -> list[dict]:
    results = []
    for item in EVAL_SET:
        print(f"\n[{item['id']}] 问：{item['question']}")

        # Step 1：用 ch5 的 RAG 管线生成答案
        answer, context = rag_answer(item["question"], return_context=True)
        print(f"答：{answer[:100]}…")

        # Step 2：关键词检查（快速、无 API 成本）
        kw_result = keyword_check(answer, item["expected_keywords"])
        print(f"关键词命中率：{kw_result['keyword_hit_rate']:.0%}  "
              f"缺失：{kw_result['missing']}")

        result = {
            "id": item["id"],
            "question": item["question"],
            "answer": answer,
            "keyword_check": kw_result,
        }

        # Step 3（可选）：LLM-as-judge 深度评分
        if use_llm_judge:
            judge = judge_answer(item["question"], context, answer)
            print(f"LLM 评分：{judge['total_score']}/10")
            result["llm_judge"] = judge

        results.append(result)

    # 汇总报告
    avg_kw = sum(r["keyword_check"]["keyword_hit_rate"]
                 for r in results) / len(results)
    print(f"\n{'='*50}")
    print(f"评估集总数：{len(results)} 条")
    print(f"平均关键词命中率：{avg_kw:.0%}")
    if use_llm_judge:
        scores = [r["llm_judge"]["total_score"] for r in results
                  if r["llm_judge"]["total_score"] is not None]
        if scores:
            print(f"平均 LLM 评分：{sum(scores)/len(scores):.1f}/10")

    return results


if __name__ == "__main__":
    # 运行完整评估（关键词检查 + LLM-as-judge）
    results = run_eval(use_llm_judge=True)
    # 输出 JSON 报告
    with open("eval_report.json", "w", encoding="utf-8") as f:
        json.dump(results, f, ensure_ascii=False, indent=2)
    print("\n评估报告已保存到 eval_report.json")
注意评估脚本复用了 ch5 的 rag_answer()——评估不是独立模块，而是套在整个管线外面的验证层。每次你改了 ch3 的 prompt 模板、ch4 的模型、ch5 的切块策略，都用这个脚本跑一遍，看指标有没有退步。

本章小结

①
LLM 评估不等于传统测试

不确定性 + 开放性，让精确匹配失效。正确答案是一个集合，评估的任务是判断"输出是否在集合里"——这是语义理解问题，不是字符串比较。

②
LLM-as-judge = 带 rubric 的 LLM 调用

评判模型按照评分标准逐条打分，扩展性好但有系统性偏见（位置、啰嗦、自我偏好）。要用人工抽样校准，不要盲目信任评判分数。

③
评估集是工程文化

每次改动都跑评估集查回归，这是 AI 工程师和调包玩家的分界线。评估集应随系统迭代持续增长。

④
离线 + 在线，两道防线

离线评估是上线前的防线，在线监控是上线后的听诊器。两者互补——只有一个都是盲飞。

本章词汇表

评估
系统性地测量 AI 系统输出质量的过程。与传统软件测试不同：LLM 输出具有不确定性和开放性，需要超越精确字符串匹配的评估手段。
LLM-as-judge
用一个语言模型（评判模型）按照评分标准（rubric）对另一个模型的输出打分的评估方法。扩展性好、可定制，但评判模型本身有系统性偏见，需要人工校准。
评分标准（rubric）
告诉评判模型"按什么维度、以什么标准打分"的结构化指令。包含维度（忠实度/完整性/相关性等）、分值范围和评分说明。rubric 的质量决定评判的质量。
忠实度
Faithfulness。RAG 系统的核心评估指标：答案中的每个事实声明是否能在检索到的上下文里找到依据。忠实度低意味着模型在幻觉，没有基于文档作答。
检索准确率
Precision@k。RAG 检索质量指标：top-k 检索结果中，与问题真正相关的片段占多大比例。高精确率意味着检索结果的噪声少。
召回率
Recall@k。RAG 检索质量指标：包含正确答案的片段，出现在 top-k 检索结果里的比例。高召回率意味着不遗漏相关信息。精确率和召回率往往互相trade-off。
评估集
Eval Set。一批"输入 + 期望行为"的样本，用于系统性评估 AI 应用的质量。每次改动（改 prompt、换模型、调参数）都跑一遍评估集检查有无退步。是建立可重复评估的基础。
回归测试
Regression Testing。每次改动后跑评估集，检查各项指标是否相比上一版本退步。目的是防止"改好一个地方、破坏另一个地方"的悄然退步。
离线评估
上线前在预先准备的评估集上运行系统并测量指标。快速、可重复、可版本间对比。是"不上线的防线"，是防止带 bug 上线的第一道关卡。
在线评估
系统上线后，通过监控真实用户行为、收集用户反馈（点赞/踩、追问）来评估质量。能发现离线评估集未覆盖的真实分布问题，是"上线后的听诊器"。
A/B测试
将用户随机分组，A组用旧版本，B组用新版本，对比关键指标（满意度、完成率）。是在线评估的最严格形式，有统计显著性保证，但需要足够的用户流量才有意义。
