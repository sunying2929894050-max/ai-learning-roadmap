先问它一个它不可能知道的问题

📋 真实场景

你把公司内部手册（合同模板、报销规定、绩效标准）存在电脑上，打开 ChatGPT 问："我们公司的年假是多少天？"

模型回答："一般而言，中国劳动法规定……"——它在背法规，完全没有回答你公司的具体政策。再问一遍，有时候它会直接给你一个听起来合理的数字，但那是它编的。

→ 这不是 bug，这是 ch1 讲过的结构性问题：模型的知识冻结在训练截止日期，对训练后产生的私有数据一无所知。你需要 RAG。
回扣 ch1：RAG 是幻觉的"补丁"
ch1 讲到幻觉时提到，模型没有实时查阅资料的能力，解法之一是在提问时把相关资料附上。RAG 正是这个机制的系统化实现——不是一次性手动附上，而是自动从知识库里检索最相关的片段，每次提问都自动附上。
◈

RAG 核心思想

RAG（检索增强生成）的逻辑极其简单：检索相关片段，塞进 prompt，让模型基于片段作答。不修改参数，不需要 GPU，只需要一个检索系统和一个 prompt 模板。

速览：RAG 做的事，用一句话说
把"闭卷考试"改成"开卷考试"——让模型考试前能翻到你指定的资料书，然后照着作答。
①
建库（离线）

把文档切成小块 → 每块变成向量 → 存入向量库。

②
检索（实时）

用户问题变成向量 → 在库中找最相似的 k 个片段（top-k 检索）。

③
生成（实时）

检索到的片段 + 用户问题 → 塞进 prompt → 调 LLM → 得到基于片段的回答。

为什么 RAG 能减轻幻觉——从参数记忆 vs 上下文记忆说起

模型有两种"知道"某件事的方式：
① 参数记忆（Parametric Memory）：训练时学进权重里的知识，固定不变，存在截止日期和遗忘率。
② 上下文记忆（Contextual Memory）：当前 prompt 里的内容，模型续写时会直接引用。

回扣 ch1 幻觉：幻觉的根源是模型在参数记忆里找不到答案却强行续写——它预测"最可能的下一个 token"，而不是"真实的答案"。

RAG 的解法：把正确答案直接放进上下文，让模型从"参数记忆续写"切换为"照着给定文本续写"。这对模型来说更容易——它只需要做信息抽取和改写，而不是凭空生成。

回扣 ch3 Prompt 是什么：RAG 的"注入上下文"本质就是在 prompt 里加了一段 <context>。我们在 ch3 已经建好了这个 prompt 模板（project/ch3-qa-prompt.txt）——RAG 需要做的，只是自动填入 {document_content}，而不是手动复制粘贴。

RAG 减轻幻觉，但不消除（诚实说明）：
• 如果检索没命中（相关片段不在库里），<context> 里是无关内容，模型仍可能回到参数记忆幻觉
• 如果模型选择无视上下文，仍会产生幻觉
• 参数记忆的错误 + 检索的错误 = 可以叠加
回扣 ch1 的结论：RAG 是减轻，不是消除。

检索怎么做：向量 + 余弦相似度

RAG 的检索不是关键词搜索，而是语义检索——这是本章最重要的技术概念，也是和 ch2 衔接最紧密的地方。

速览：ch2 的向量相似度，用在了 RAG 检索上
直接回扣 ch2 Embedding
ch2 演示了：把"cat"和"dog"都转成向量后，余弦相似度高达 0.92——即使它们字面上没有任何共同字符。RAG 检索做的是完全一样的事，只是把"单词"换成了"文档段落"：用户的问题 → 向量，每个文档片段 → 向量，余弦相似度最高的片段 = 最可能包含答案的片段。
语义检索为什么比关键词检索更好——从 ch2 的分布假设说起

回到 ch2 Embedding：语义坐标 的核心结论：Embedding 把词（或句子）映射到高维向量空间，语义相似的内容在向量空间里距离近。这个"相似"来自分布相似性——出现在类似上下文里的词，向量方向接近。

在 RAG 里，这个机制被直接复用到段落级别：
• 文档里有一段："员工每满一年享有5天带薪年假"
• 用户问题："公司年假政策是什么？"
• 关键词搜索：两者共享词"年假"，可以匹配
• 语义搜索：即使用户问"我能请几天年假"（没有"政策"二字），向量仍然相近，依然能检索到

具体流程（和 ch2 余弦相似度公式完全一致）：

建库阶段（一次性）：
E_chunk = embed_model(chunk_text) # → 1536维向量（或 3072、768，取决于模型）
对每个片段都算一遍，把所有向量存起来。

查询阶段（每次提问）：
E_query = embed_model(user_question) # 同一个模型
sim_i = cosine(E_query, E_chunk_i) # = ch2 里的余弦相似度公式
top_k = argsort(sim)[-k:] # 取相似度最高的 k 个片段

为什么强调"同一个嵌入模型"？
向量空间是由训练该嵌入模型的数据决定的。用 A 模型嵌入文档、用 B 模型嵌入问题——它们生活在不同的向量空间里，余弦相似度毫无意义。这是一个常见的工程错误。

嵌入模型 vs 生成模型：
你在 ch4 调用的 deepseek-chat 是生成模型（输出文字）。嵌入阶段用的是嵌入模型（输出向量），如 text-embedding-3-large（OpenAI）或 BAAI/bge-m3（开源）。两者是不同的 API 调用，价格也不同（嵌入通常便宜很多）。
OpenAI Embeddings 文档（支持中文） BGE-M3：多语言开源嵌入模型（支持中文）

切块（Chunking）与向量库

原始文档不能整个喂给嵌入模型——它太长。也不该整个放进 prompt——放不下，而且会稀释相关信息。解法是先切块，再检索精确片段。

速览：为什么要切块，怎么切
参数太小太大经验推荐
块大小缺乏上下文，检索到片段不完整检索精度低，无关内容多300~500 token
重叠量0 重叠：跨块边界的信息丢失冗余多，库膨胀50~100 token
切块大小与重叠的核心权衡

回扣 ch4 Context Window：大模型能处理的最大 token 数是有限的（如 128K）。把整本文档放进一个 prompt 通常超出限制；即使不超，大量无关内容会干扰模型定位答案（"Lost in the Middle"现象，ch3 讲过）。所以必须切块，只传最相关的几块。

块大小的两端
• 过小（如 50 token）：每块只有两三句话，缺乏上下文。检索到"年假5天"这个片段，但没有主语，不知道是哪个岗位的政策。生成质量差。
• 过大（如 2000 token）：每块包含多个主题，嵌入向量被"平均化"，无法精确捕捉其中一个主题的语义。检索精度大幅下降。

重叠（Overlap）的作用
假设一句重要的话"A 类员工享有10天年假，B类5天"恰好跨越块 N 和块 N+1 的边界：没有重叠时，两块各拿到半句，都不完整；有重叠时，两块里至少有一块包含这整句话。
代价：会存两份重叠区域的向量，略微增加存储和建库时间，通常值得。

向量库（Vector Database）
片段数量少时（几百块），可以直接把所有向量算一遍余弦相似度（暴力检索）。片段超过万级，每次查询都暴力检索太慢。向量库（FAISS / Chroma / pgvector）内部使用近似最近邻（ANN）算法——用少量精度损失换取数量级的速度提升。

三种常见向量库对比：
• FAISS（Meta）：纯内存，不持久化，适合原型和离线批处理，C++ 核心速度极快
• Chroma：Python 原生，本地文件持久化，内置嵌入 API，适合快速原型和单机部署
• pgvector：PostgreSQL 插件，适合已有 PG 数据库的生产系统，SQL 查询语法，数据一致性有保障
FAISS GitHub（Meta 开源） Chroma 文档（Python 友好的向量库）

四种常见失败模式（诚实版）
✗
检索未命中

问题的答案不在库里，或答案所在的片段被切块时被破坏。检索到的 top-k 全是无关内容 → 模型仍会幻觉。

✗
模型无视上下文

模型的参数记忆和上下文矛盾时，有时会选择参数记忆。越"确信"的知识越容易压制 context。
缓解：prompt 里明确"只使用以下内容回答，如没有则说不知道"（就是 ch3 模板的设计）。

✗
块边界截断

关键信息横跨两个块，两个块各自检索到都只有半句话。加重叠（overlap）是主要缓解手段。

✗
嵌入模型不匹配

用 A 模型嵌入文档、用 B 模型嵌入查询——向量空间不同，余弦相似度无意义，检索完全失效。

检索未命中是最常见也最难发现的失败

RAG 系统的整体质量上限由检索质量决定——LLM 再强，拿到错误的 context 也无能为力。但检索失败通常不会报错：向量库总会返回"最相似"的 k 个片段，哪怕那 k 个片段和问题毫无关系。从外部看，系统正常运行；从输出看，模型给出了一个听起来合理的错误答案。

这就是为什么 ch7（评估）必须存在：需要系统性地测量"检索命中率"（Recall@k：正确答案出现在 top-k 里的比例）和"答案准确率"，而不是人工抽查几个例子就认为 RAG 工作正常了。

检索质量的几个提升方向：
• HyDE（Hypothetical Document Embedding）：先让 LLM 根据问题"假装"生成一段答案，用这段假答案的向量去检索（因为假答案的向量比问题的向量更接近真实文档）
• 查询重写（Query Rewriting）：用 LLM 把用户的口语化问题改写成更像文档语言的形式，再检索
• 混合检索：语义检索 + 关键词检索（BM25）结果融合，互补覆盖

"""
文档助手 — ch5 产物：RAG 管线
依赖：pip install openai chromadb
嵌入模型用 OpenAI text-embedding-3-small（DeepSeek 暂无嵌入 API）
"""
import os
from openai import OpenAI
import chromadb

embed_client = OpenAI()          # 用 OPENAI_API_KEY
chroma = chromadb.Client()
collection = chroma.get_or_create_collection("docs")

# ── 切块函数 ──
def chunk_text(text: str, size: int = 400, overlap: int = 80) -> list[str]:
    chunks, start = [], 0
    while start < len(text):
        end = start + size
        chunks.append(text[start:end])
        start += size - overlap
    return chunks

# ── 入库 ──
def index_document(doc_id: str, text: str) -> None:
    chunks = chunk_text(text)
    embeddings = embed_client.embeddings.create(
        model="text-embedding-3-small",
        input=chunks,
    ).data
    collection.add(
        ids=[f"{doc_id}_{i}" for i in range(len(chunks))],
        embeddings=[e.embedding for e in embeddings],
        documents=chunks,
    )
    print(f"已入库 {len(chunks)} 个片段")

# ── 检索 + 生成 ──
def rag_answer(question: str, k: int = 3) -> str:
    q_vec = embed_client.embeddings.create(
        model="text-embedding-3-small", input=[question]
    ).data[0].embedding

    results = collection.query(query_embeddings=[q_vec], n_results=k)
    context = "\n\n".join(results["documents"][0])

    # 直接复用 ch3 的 prompt 模板
    with open("ch3-qa-prompt.txt") as f:
        template = f.read()
    prompt = template.replace("{document_content}", context)
    prompt = prompt.replace("{user_question}", question)

    from openai import OpenAI as DSClient
    ds = DSClient(
        api_key=os.environ["DEEPSEEK_API_KEY"],
        base_url="https://api.deepseek.com",
    )
    resp = ds.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "user", "content": prompt}],
        max_tokens=512,
    )
    return resp.choices[0].message.content

if __name__ == "__main__":
    # 示例：入库并查询
    with open("my_document.txt") as f:
        doc = f.read()
    index_document("my_doc", doc)
    print(rag_answer("文档里提到的主要结论是什么？"))
注意 ch3 的 prompt 模板被直接复用了（ch3-qa-prompt.txt），这正是当初设计"只使用 context 里的信息回答"约束的原因——RAG 系统天然需要这个约束来防止模型绕开检索结果凭空作答。

本章小结

①
RAG = 检索 + 上下文注入 + 生成

不改模型参数，只改 prompt 内容。把 ch1 的幻觉补丁、ch2 的向量检索、ch3 的 prompt 模板拼成一条管线。

②
检索质量是上限

检索未命中，LLM 再强也无能为力。用 ch2 的余弦相似度做语义检索，比关键词匹配更鲁棒；同一嵌入模型入库和查询。

③
切块是精度和覆盖的权衡

块太小缺上下文，块太大检索精度低。overlap 防止边界截断。向量库（FAISS/Chroma）解决大规模高速检索问题。

④
RAG 减轻幻觉，不消除

这一点回扣 ch1 的结论。需要系统性评估（ch7）才能知道 RAG 系统到底工作得多好，不能靠主观感受。

本章词汇表

RAG
检索增强生成（Retrieval-Augmented Generation）。在推理时从外部知识库检索相关片段，注入 prompt 上下文，让模型基于检索到的内容作答。不改变模型参数，不需要 GPU。
语义检索
基于向量余弦相似度的检索方式。把查询和文档片段都嵌入到同一向量空间，找语义上最近的片段，能匹配字面不同但含义相近的内容。区别于关键词检索（BM25）。
切块（Chunking）
把长文档切成固定大小的小段（chunk）以便嵌入和检索。关键参数：块大小（通常 300-500 token）和重叠量（通常 50-100 token）。
向量库
专门存储和检索向量的数据库（FAISS、Chroma、pgvector 等），使用近似最近邻（ANN）算法高效返回 top-k 相似向量。比暴力余弦检索快数量级。
top-k 检索
从向量库返回与查询最相似的 k 个文档片段。k 通常取 3-5，太小可能漏掉答案，太大会引入噪声、增加 token 成本。
上下文注入
把检索到的片段拼接进 prompt 的 <context> 区域，让模型基于这段文本作答而非靠参数记忆。是 RAG 查询阶段的核心步骤，直接复用 ch3 的 QA prompt 模板。
嵌入模型
将文本转换为向量的专用模型（如 text-embedding-3-small、BGE-M3），不同于生成模型（如 deepseek-chat）。输出是固定维度的浮点向量，不产生文字。
参数记忆
模型权重里固化的知识，来自预训练语料，有截止日期。与"上下文记忆"（当前 prompt 里的内容）相对。RAG 把私有知识从参数记忆转移到可更新的上下文记忆。
