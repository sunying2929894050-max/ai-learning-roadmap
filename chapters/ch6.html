工具调用与 Agent

给大模型配上工具，让它自己决定调什么、按什么顺序——这就是 Agent。本章把 ch1 的 token 生成、ch3 的格式续写、ch4 的 API 调用成本、ch5 的上下文回灌全部串起来，组成一条可运转的 Agent 管线。

先问它一件它做不到的事

🧪 三个实验

实验一：问它现在几点
"现在是几点？"——模型的回答通常是"我没有访问实时数据的能力"，或者给你一个截止日期附近的随机猜测。它真的不知道，因为推理时没有时钟输入。

实验二：让它做精确计算
"31 × 97 × 43 等于多少？"——语言模型不是计算器，它在 token 空间预测下一个字符，多位乘法经常出错。你信任这个数字吗？

实验三：问它私有信息
"我们公司的年假政策？"——和 ch5 的场景完全一样，它不知道你的私有数据，会给出通用回答或幻觉内容。

→ 这三件事都有解法：给模型配工具。配上时钟工具、计算器工具、文档检索工具——让工具去做工具该做的事，让模型做模型该做的事（理解意图、选择工具、整合结果）。这就是工具调用与 Agent。
◈

工具调用的本质

工具调用（Tool Use / 函数调用）听起来像"模型去执行函数"——这个直觉是错的。理解它的真相，才能理解为什么 Agent 的行为有时不可预测。

速览：工具调用的真实流程
①
你告诉模型有哪些工具

在 prompt 或 API 参数里描述工具名称、功能、参数格式。

②
模型输出一段 JSON 请求

模型不执行任何代码——它只是生成一段结构化文本，内容是"我想调用工具 X，参数是 Y"。

③
你的代码执行工具

解析模型输出的 JSON → 真正调用函数/API → 得到结果。

④
把结果塞回上下文

工具结果作为新的消息附到对话里，模型接着续写，给出最终回答或下一步工具调用。

工具调用的本质：模型只输出请求，执行在你的代码里

这是本章最核心的认知颠覆。把它拆到最底层：

回扣 ch1 训练与推理：模型在推理时做的事情只有一件——根据当前所有 token，预测下一个最可能的 token，然后循环。它没有系统调用权限，没有网络连接，没有 Python 解释器。所谓"模型调用工具"是一个方便的说法，真相是：模型生成了一段看起来像工具调用的文本，你的编排代码读取这段文本、执行真实的函数、再把结果放回去。

回扣 ch3 Prompt 是什么：工具调用的格式（JSON schema、字段名、参数类型）之所以能工作，是因为训练数据里有海量类似格式的文本，模型学会了"在这种语境下，下一段内容应该长这样"。这仍然是 token 续写，只是续写的内容恰好是合法的 JSON。

用代码展示这个流程：
# 模型收到 prompt，输出这样一段 token 序列：
# {"action":"calculator","input":{"expression":"31*97"}}

# ↑ 这不是函数调用——这只是一段字符串
# 你的代码负责：
action = json.loads(model_output) # 解析 JSON
result = run_tool(action["action"], # 真正执行工具
                 action["input"])
messages.append({"role":"tool", # 把结果塞回上下文
                 "content":str(result)})
next_response = call_llm(messages) # 再次调 LLM

为什么这个区分重要？
• 模型输出的 JSON 可能畸形（缺括号、错字段名）——你的解析器要处理异常
• 模型可能"瞎编"一个不存在的工具名——你的路由要防御性检查
• 模型可能生成参数值看起来合理但实际有害——工具执行前要验证

所有这些问题的根源是同一个：模型只是在续写，不保证续写的内容可执行或安全。

Agent 循环：ReAct 模式

Agent 和单次工具调用的区别在于循环——模型可以多步使用工具，每步看到上一步的结果再决定下一步。最常见的实现是 ReAct 模式（Reasoning + Acting）。

速览：ReAct 循环的三个节拍
💭
Reasoning
分析任务，决定
调哪个工具
🔧
Acting
输出工具调用 JSON
（你的代码执行它）
📊
Observing
工具结果注入上下文
模型看到后再推理

循环直到：模型输出"最终答案"，或达到最大步数 MAX_STEPS 限制。

Agent 循环的底层：每一步都是一次 ch4 的 API 调用

把 ReAct 循环拆开看，它就是一个 while 循环 + 不断增长的 messages 数组：

messages = [{"role":"user","content":question}]
for step in range(MAX_STEPS):
  response = call_llm(messages) # ch4 的 API 调用
  action = parse_json(response) # 解析模型输出
  if action["type"] == "final_answer":
    return action["content"]
  result = run_tool(action) # 执行工具
  messages.append(assistant=response) # 把模型输出存入历史
  messages.append(user=result) # 把工具结果回灌

回扣 ch4 Token 与成本：注意每次循环 messages 数组都在增长——思考+行动+观察+思考+行动+观察……每一步都要带着完整历史发给 API。一个5步的 Agent 任务，发送的 token 总量 ≈ 5步 × 平均上下文长度（且后几步更长）。成本随步数超线性增长，这是 Agent 在生产中的主要费用来源。

回扣 ch5 RAG 核心思想：把工具结果"回灌"进 messages，本质上和 RAG 的"上下文注入"是同一个操作——都是把外部获取的信息放进 prompt 的上下文区域，让模型能"看到"它并续写。Agent 可以看作是动态的、多步骤的 RAG：不是一次性检索一次性注入，而是每步按需检索，结果层层累积。

"编排代码"是 Agent 的大脑外壳
模型本身是无状态的——每次 API 调用完全独立。所谓"Agent 在思考多步任务"，实际上是你写的编排代码在维护 messages 历史、决定循环继续还是终止、路由工具调用到具体函数。模型只做一件事：在给定对话历史下预测下一段文本。"Agent 的智能"一半来自模型，一半来自你的编排逻辑。

工具描述与工具选择

模型选择"调哪个工具、传什么参数"，完全依赖你对工具的工具描述。描述写得好，选对；写得模糊，选错。这和 ch3 写好 prompt 的逻辑完全一致。

速览：工具描述的三要素
①
名称（Name）

简洁、唯一、动词/名词清晰。好：search_documents。差：do_stuff。

②
描述（Description）

说清楚"什么时候用这个工具"。好的描述直接回答"我应该在什么情况下调用它"。这是模型选择工具最依赖的字段。

③
参数 Schema（Input Schema）

每个参数要有类型（string / number / boolean）和描述。required 字段列出必填项，optional 说清楚默认值。

工具描述的质量直接决定 Agent 的准确率

回扣 ch3 提示词工程：模型选工具的过程本质上是在做"分类"任务——把用户意图分类到某个工具。这个分类的依据是描述文字，和 few-shot prompt 的例子起到的作用相同：给模型足够的语义信号，让它在 token 续写时走向正确的"分支"。

好工具描述 vs 差工具描述：

差："calculator": "does math"
好："calculator": "当需要精确数值计算时使用，如乘法、除法、开方。不适合单位换算或文字推理。"

差："search_docs": "searches"
好："search_docs": "在公司内部文档库中语义搜索。适合回答'公司政策是什么''合同条款是什么'等问题。不适合搜索互联网或通用知识。"

工具数量与歧义：
工具列表越长，模型误选的概率越高。生产实践中的建议：
• 每个工具功能单一、边界清晰
• 描述里明确说"不适合什么场景"，防止过度调用
• 工具数量超过 10-15 个时，考虑分层路由（先让模型选类别，再在类别内选工具）

失败模式（诚实版）

Agent 比单次调用强大，也比单次调用脆弱。每增加一步，就多一个出错的机会。理解失败模式是在生产中使用 Agent 的前提。

五种常见失败模式
✗
选错工具

模型把"计算 3 × 4"发给了 search_docs 工具——因为工具描述不清晰，或任务描述歧义。

✗
瞎编参数

工具需要合法的日期格式，模型传了 "yesterday"；或把字段名拼错了。JSON 解析失败，Agent 陷入错误处理循环。

✗
死循环

工具每次返回"未找到"，模型换个角度再试，还是"未找到"，再试……没有终止条件就无限循环。必须设 MAX_STEPS 硬上限。

✗
成本爆炸

回扣 ch4：每步都带完整历史，5步任务的 token 消耗可能是单次调用的 10-20 倍。没有步数上限和成本监控的 Agent 可能产生意外账单。

✗
工具报错后幻觉

工具调用失败，模型没有得到真实结果，但仍然"续写"了一个听起来合理的答案——靠参数记忆凑出来的幻觉。回扣 ch1 + ch5 的结论。

为什么 Agent 的错误比单次调用更难察觉

单次 LLM 调用的错误通常是"答案不对"——用户问一个问题，得到一个错误答案，相对容易发现。

Agent 的错误更隐蔽：
• 中间步骤出错：工具在第2步用了错误参数，第4步的"正确格式"答案实际上是基于错误数据推导的
• 错误被"合理化"：模型很擅长把任何工具结果都整合进一个听起来合理的叙述
• 多步积累偏差：每步有1%的偏差，5步后偏差叠加

这就是为什么 ch7（评估）在 Agent 场景下更重要：需要对每个中间步骤（工具选择是否正确、参数是否合理、工具结果是否被正确使用）做系统性评估，而不只是看最终答案。

生产环境的防护层：
• MAX_STEPS 硬限制（防死循环）
• 工具执行前参数验证（防瞎编参数）
• 工具执行超时（防外部 API 挂起）
• 成本预算上限（防账单爆炸）
• 高风险操作（发邮件、删数据）要人工确认检查点

"""
文档助手 — ch6 产物：Agent 循环 + 工具调用
来源：AI 学习路线 ch6 工具调用与 Agent

依赖：pip install openai chromadb
用法：
  export OPENAI_API_KEY="sk-..."   # 嵌入模型
  export DEEPSEEK_API_KEY="sk-..."  # 生成模型
  python3 ch6-agent.py
"""

import os, json, re
from openai import OpenAI

# ── 复用 ch5 的 RAG 检索（已入库的 collection） ──
from ch5_rag_pipeline import collection, embed_client as _emb

def _search_docs(query: str, k: int = 2) -> str:
    """把 ch5 的向量检索包装成 Agent 工具。"""
    q_vec = _emb.embeddings.create(
        model="text-embedding-3-small", input=[query]
    ).data[0].embedding
    results = collection.query(query_embeddings=[q_vec], n_results=k)
    docs = results["documents"][0]
    if not docs:
        return "未在文档库中找到相关内容。"
    return "\n\n".join(f"[片段{i+1}] {d}" for i, d in enumerate(docs))

def _calculator(expression: str) -> str:
    cleaned = re.sub(r"[^0-9+\-*/.() ]", "", expression)
    try:
        result = eval(cleaned, {"__builtins__": {}})
        return f"{expression} = {result}"
    except Exception as e:
        return f"计算失败：{e}"

def _get_time() -> str:
    from datetime import datetime
    return datetime.now().strftime("当前时间：%Y-%m-%d %H:%M:%S（本地）")

# ── 工具路由表 ──
TOOLS = {
    "calculator": {
        "desc": "精确计算数学表达式。适合乘除加减、开方等数值运算。input: {\"expression\":\"31*97\"}",
        "fn": lambda inp: _calculator(inp["expression"]),
    },
    "get_time": {
        "desc": "获取当前日期和时间。适合需要知道今天日期或现在时刻的问题。input: {}",
        "fn": lambda _: _get_time(),
    },
    "search_docs": {
        "desc": "在公司内部文档库（ch5 知识库）中语义搜索。适合回答公司政策、合同条款等私有信息。input: {\"query\":\"年假政策\"}",
        "fn": lambda inp: _search_docs(inp["query"]),
    },
}

SYSTEM_PROMPT = (
    "你是一个使用工具完成任务的 AI Agent。\n\n"
    "可用工具：\n"
    + "\n".join(f"- {n}: {t['desc']}" for n, t in TOOLS.items())
    + "\n\n每次回复必须且只能是以下格式的 JSON（不加任何额外文字）：\n"
    "调用工具：{\"thought\":\"原因\",\"action\":\"工具名\",\"input\":{...}}\n"
    "最终答案：{\"thought\":\"已有所有信息\",\"action\":\"final_answer\",\"content\":\"答案\"}"
)

ds = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
)

def _parse_json(text: str) -> dict:
    """鲁棒解析：先直接 parse，再从文本中提取 {...}。"""
    try:
        return json.loads(text.strip())
    except json.JSONDecodeError:
        m = re.search(r'\{.*\}', text, re.DOTALL)
        if m:
            return json.loads(m.group())
        return {"action": "final_answer", "content": text}

def run_agent(question: str, max_steps: int = 5) -> str:
    """ReAct 循环：思考 → 调工具 → 观察 → 再思考……"""
    messages = [{"role": "user", "content": question}]

    for step in range(max_steps):
        # ── 每步都是一次 ch4 的 API 调用 ──
        resp = ds.chat.completions.create(
            model="deepseek-chat",
            messages=[{"role": "system", "content": SYSTEM_PROMPT}] + messages,
            max_tokens=512,
        )
        raw = resp.choices[0].message.content.strip()
        print(f"\n[步骤 {step+1}] 模型输出：{raw}")

        action = _parse_json(raw)

        if action.get("action") == "final_answer":
            return action.get("content", "")

        # ── 执行工具 ──
        tool_name = action.get("action", "")
        tool_input = action.get("input", {})
        if tool_name not in TOOLS:
            tool_result = f"错误：工具 '{tool_name}' 不存在，可用：{list(TOOLS.keys())}"
        else:
            tool_result = TOOLS[tool_name]["fn"](tool_input)
            print(f"[工具结果] {tool_result}")

        # ── 把工具结果回灌进上下文（ch5 的上下文注入模式） ──
        messages.append({"role": "assistant", "content": raw})
        messages.append({"role": "user", "content": f"[工具结果] {tool_result}"})

    return "已达最大步数，无法完成任务。"

if __name__ == "__main__":
    for q in ["现在几点？", "31 × 97 × 43 = ?", "公司年假政策？"]:
        print(f"\n{'='*50}\n问：{q}")
        print(f"答：{run_agent(q)}")
注意代码里两处注释回扣：# ch4 的 API 调用 和 # ch5 的上下文注入模式——Agent 循环在工程上正是把两者组合：ch4 给了调 LLM 的能力，ch5 给了"把外部结果塞进上下文"的模式，再加一个 for 循环就成了 Agent。

本章小结

①
工具调用 = 模型生成 JSON 请求，你的代码执行

模型从不"运行"任何代码，它只是生成 token。"调用工具"是你的编排代码在执行。这个认知决定了如何设计防御性系统。

②
Agent = ReAct 循环 + 不断增长的上下文

每步是一次 ch4 的 API 调用，每步把结果回灌进 messages（ch5 的上下文注入模式）。循环本身是你写的，不是模型内置的。

③
工具描述决定工具选择质量

本章词汇表

工具调用
让语言模型使用外部工具（计算器、搜索、API）的机制。模型输出一段结构化的调用请求（JSON），你的代码执行真实函数、把结果回灌进上下文。模型本身不执行任何代码。
函数调用
Function Calling。工具调用的另一种说法，来自 OpenAI 最初引入时的命名。和"工具调用"（Tool Use，Anthropic 的命名）本质相同，均指"模型输出请求→代码执行→结果回灌"这个流程。
Agent
能自主决定调用哪些工具、按什么顺序、多步完成复杂任务的 AI 系统。不同于单次回答：Agent 在完成任务前可进行多轮思考-行动-观察循环。"自主"的程度取决于编排代码给了它多少决定权。
ReAct
Reasoning + Acting。一种 Agent 设计模式：让模型交替进行推理（分析任务、决定下一步）和行动（调用工具）。每次行动后模型观察工具结果再推理，循环直到任务完成。2022年提出，目前最主流的 Agent 框架基础。
Agent 循环
实现 ReAct 的编排代码：while 循环，每次迭代调一次 LLM API、执行工具、把结果追加进 messages，直到模型输出"最终答案"或达到 MAX_STEPS 上限。循环是你写的，不是模型内置的。
工具描述
告诉模型"有哪些工具、各自做什么、何时用、参数格式是什么"的文字说明。模型根据工具描述选择调用哪个工具。描述质量直接决定工具选择准确率，和 prompt 工程的逻辑完全一致。
动作 / 观察
ReAct 循环的两个节拍。动作（Action）：模型输出要调用的工具和参数。观察（Observation）：工具执行后返回的结果，追加进 messages 让模型在下一步"看到"。
编排
Orchestration。管理多个 LLM 调用、工具调用、消息历史的代码层。在 Agent 系统里，编排代码负责：维护 messages、路由工具调用、控制循环终止条件、处理错误。LangChain、LlamaIndex 等框架本质上是编排框架。
