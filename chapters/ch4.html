你点发送的那一刻，底层发生了什么

🔍 拆开这 0.3 秒

你在 ChatGPT / DeepSeek 输入框里打完问题，按下回车。0.3 秒后，第一个字出现，然后一个词一个词地蹦出来。感觉像魔法——但底层不是。

这 0.3 秒里，你的浏览器做了一次 HTTP 请求：把你的消息打包成 JSON，POST 到 OpenAI / DeepSeek 的服务器，服务器把这段文本喂给模型，模型开始一个 token 一个 token 地生成，生成一个就推回来一个，浏览器收到就渲染。

→ 这和你用 Python 调用同一个 API 没有本质区别。理解这条链路，你就理解了"接入大模型 API"的全部。
①
打包请求

浏览器（或你的 Python 代码）把消息历史序列化成 JSON，加上 API key 和参数，构成一个 HTTP POST 请求。

②
服务器鉴权

API 服务器读取请求头里的 API key，验证有效性，确认账户额度，记录这次调用的成本。

③
模型推理

消息序列被 tokenize，送进 GPU 集群做推理。模型逐 token 生成回复（回扣 ch2 自回归）。

④
流式返回

每生成一个 token 或一小块，服务器立刻通过保持住的 HTTP 连接推回客户端（SSE 流式）。你看到的"一个词一个词蹦出来"就是这个。

API 调用到底是什么

API 听起来很神秘，但它就是一个约定：你按规定格式发一个 HTTP POST 请求，服务器按规定格式返回一个 JSON 响应。仅此而已。

速览：一次完整的 API 调用 
# POST https://api.deepseek.com/chat/completions
# Headers:
#   Content-Type: application/json
#   Authorization: Bearer sk-xxxxxxxxxxxxxxxx

# Body (JSON):
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system",  "content": "你是严谨的文档助手。"},
    {"role": "user",    "content": "合同的违约条款是什么？"},
    {"role": "assistant","content": "根据第五条..."},
    {"role": "user",    "content": "具体赔偿金额呢？"}
  ],
  "max_tokens": 1024,
  "stream": true
}
HTTP 请求的四个要素（在这里第一次需要，就在这里讲清）

① URL / Endpoint
Endpoint 就是目标地址，如 https://api.deepseek.com/chat/completions。"chat/completions"告诉服务器你要调用哪个功能（聊天完成），而不是图像生成或语音转录。

② HTTP 方法 = POST
HTTP 有多种方法：GET 是"读取"（浏览器打开网页用的），POST 是"提交数据"。API 调用用 POST，因为你要把数据（消息历史 + 参数）发到服务器。GET 请求没有 body，放不了这么多内容。

③ Headers（请求头）
HTTP header 是请求的"元数据"，格式是 键: 值。两个必须的 header：
• Content-Type: application/json — 告诉服务器 body 里装的是 JSON 格式
• Authorization: Bearer sk-xxx — 你的身份证明（见下一节）

④ Body（请求体）= JSON
JSON 是一种文本格式，用大括号 {} 包对象，中括号 [] 包数组，键值用冒号分隔。大模型 API 的 body 核心是 messages 数组——这正是 ch2 讲过的那条 token 序列的文本表示：

每一条消息都有 role（谁说的：system / user / assistant）和 content（说了什么）。API 收到后会把所有消息按顺序 tokenize、拼接，送进模型——它和 ch2 里讲的"同一条 token 流"完全对应。

响应 JSON 的结构
服务器返回：
{"choices":[{"message":{"role":"assistant","content":"..."},"finish_reason":"stop"}],"usage":{"prompt_tokens":234,"completion_tokens":87,"total_tokens":321}}

usage 字段直接告诉你这次用了多少 token，是对账和成本监控的依据。

API Key 与鉴权

API key 是你在 API 服务商处的身份证明，每一次 API 调用都要带上它。一个字符都不能错，一个字符都不能泄露。

速览：key 放在哪、有什么用 
# key 放在 Authorization header 里，格式固定：
Authorization: Bearer sk-a1b2c3d4e5f6...

# 服务器收到后：
# 1. 验证 key 存在且未被吊销
# 2. 找到对应账户
# 3. 检查余额是否足够
# 4. 记录本次调用 token 数，从余额扣款
# 5. 把请求转发给模型
Bearer token：HTTP 鉴权方案之一。"Bearer"意为"持有者"——持有这个 token 的人，就被当作合法用户。服务器不问你是谁，只认 token。
为什么 API key 必须绝对保密

Bearer token 的设计哲学是"谁持有就代表谁"——服务器没有办法区分"合法持有者"和"非法持有者"，它只验证 token 的合法性，不验证发送者的身份。

这意味着，如果你的 key 被拿走：
• 对方可以用你的账户和余额无限量调用 API，直到余额耗尽（或你设置的速率限制到达）
• 你的调用历史（包括发过去的所有 prompt 和回复）可能被访问
• 服务商账单里的成本爆炸——而且你很可能不会立即发现
• 吊销 key 后要重新生成、更新所有用到它的地方

常见泄露路径：
① 把 key 直接硬编码进代码，提交到 GitHub（GitHub 有爬虫专门扫这类 key，泄露后数分钟内就会被盗用）
② 粘贴进不可信的网站（"帮你测试 key 是否有效"类服务）
③ 把含 key 的日志文件上传到云端

生产级最佳实践：
• key 只放在环境变量或密钥管理服务（如 AWS Secrets Manager）里
• 代码里通过 os.environ["API_KEY"] 读取，绝不硬编码
• 不同环境（开发/测试/生产）用不同的 key，权限分开
• 定期轮换 key；设置消费告警（服务商通常支持）
• 前端代码永远不能含有 key——浏览器开发者工具能看到所有前端代码

流式输出（SSE）：文字为何一个词一个词蹦出来

这不是动画效果，也不是服务器在"假装流式"——它真的是模型每生成一个 token 就推一个。

速览：两种响应模式对比
非流式（stream: false）

服务器等模型生成完整回复后，一次性返回全部内容。用户盯着空白等 10-30 秒，然后整段文字突然出现。

流式（stream: true，SSE）

生成一个 token 就立刻推回客户端。用户几乎立即看到第一个词，然后持续看到内容增加。感知速度快 10 倍以上。

SSE 的工作方式，以及为什么它和模型的生成方式天然吻合

回到 ch2 自回归生成：模型本就是逐 token 生成的——每次 forward pass 产生一个 token，追加到序列，再做下一次 forward pass。这不是流式的"模拟"，而是模型工作的物理方式。

SSE（Server-Sent Events） 是 HTTP 协议的一种用法：服务器和客户端之间的 HTTP 连接保持打开不关闭，服务器可以持续往里推送数据行，每行格式是 data: {...}\n\n。客户端（浏览器或 Python 代码）通过监听这条连接，实时读取每一行。

大模型 API 流式响应的每一行格式（以 OpenAI 兼容格式为例）：
data: {"choices":[{"delta":{"content":"你"},"index":0}]}
data: {"choices":[{"delta":{"content":"好"},"index":0}]}
data: [DONE]

每个 delta.content 就是新生成的那一个（或几个）token 的文本。客户端把收到的 delta 追加到显示区域，用户就看到"字在蹦"。

从 Python 读流式响应： 
with client.messages.stream(
    model="claude-opus-4-8",
    max_tokens=1024,
    messages=[{"role":"user","content":"讲一个故事"}]
) as stream:
    for text in stream.text_stream:
        print(text, end="", flush=True)  # 每来一块立刻打印
延伸：为什么 stream: false 有时更合适？
批量处理场景（不需要实时显示给用户）、结果要完整后才能处理（如 JSON 解析）、调试时不希望分块——这些场景用非流式更简单。

Token 与成本：每次点发送花了多少钱

大模型 API 按 token 计费，输入和输出分开算，上下文历史每轮都要重新计入。

速览：DeepSeek V3 计费示例
类型单价（约）1000次对话估算
输入 token¥0.001 / 千 token取决于对话长度
输出 token¥0.002 / 千 token（输出通常比输入贵）
一次普通问答约 500 输入 + 200 输出 = ¥0.0009（不到一厘钱）
10元人民币能做约 10,000 次普通问答实验。学习阶段完全够用。
为什么多轮对话的成本会快速累积

回到 ch2 自回归与 ch2 token 概念：每次 API 调用，你发送的 messages 数组里包含完整的对话历史——模型没有"记忆"，它只能通过每次重新读入历史来"记住"前文。

这意味着：
• 第 1 轮：发 100 token 历史 + 50 token 新问题 = 150 输入 token
• 第 2 轮：发 150 + 200（第1轮回复）+ 50 新问题 = 400 输入 token
• 第 10 轮：可能已经积累了 3000+ 输入 token，大部分都是"历史"

Context Window（上下文窗口）：模型能处理的最大 token 数，如 128K。超出后，早期内容被截断——这就是为什么超长对话里模型会"忘记"开头说的事。

成本控制实践：
• 截断历史：只保留最近 N 轮对话，不发全量
• 摘要历史：用模型先把旧历史总结成短文，再放回 messages
• 结构化输出：让模型直接输出 JSON 而非长篇解释，减少输出 token
• 缓存（Prompt Caching）：部分服务商支持对 system prompt 等固定前缀做 token 缓存，重复调用时输入 token 费用打折（Anthropic 支持此功能）

输入 vs 输出 为什么定价不同？
输入 token 在一次 forward pass 里并行处理（KV cache），计算量相对固定。输出 token 每个都要做一次完整的 forward pass（自回归），计算量是线性叠加的。所以输出通常贵 1.5~4 倍。

如果你已经填入了 key，下面的代码现在就能跑：把 ch3 模板里的 {document_content} 换成你的文档内容，{user_question} 换成问题，粘进去运行。
📄 project/ch4-api-client.py（下一步产物预览） 
import os
from openai import OpenAI  # DeepSeek 兼容 OpenAI SDK

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],   # 从环境变量读，不要硬编码
    base_url="https://api.deepseek.com",
)

# 读取 ch3 的 prompt 模板
with open("ch3-qa-prompt.txt") as f:
    template = f.read()

def answer_question(document_content: str, user_question: str) -> str:
    prompt = template.replace("{document_content}", document_content)
    prompt = prompt.replace("{user_question}", user_question)

    response = client.chat.completions.create(
        model="deepseek-chat",
        messages=[{"role": "user", "content": prompt}],
        max_tokens=512,
        stream=False,
    )
    return response.choices[0].message.content

if __name__ == "__main__":
    doc = "第一条：甲方须在签约后30日内支付定金50%。第五条：任一方违约须赔偿对方损失的200%。"
    q   = "违约赔偿比例是多少？"
    print(answer_question(doc, q))
ch5（RAG）将把这个 answer_question 函数变成真正的文档检索管道——不再靠手动粘贴 document_content，而是自动从向量数据库里检索最相关的段落。

本章小结

①
API = 一次 POST + 一个 JSON body

HTTP 请求并不神秘：URL 定位服务，header 携带 key，body 传消息历史。响应里的 usage 字段告诉你花了多少 token。

②
Key = 支票本，要像密码一样保管

Bearer token 机制让任何持有 key 的人都能以你的身份消费。永远不要把 key 放进代码仓库、URL、前端文件，或粘贴进不可信的网站。

③
流式是模型工作的自然方式

自回归生成本就逐 token 产出，SSE 让每个 token 立即推回客户端。感知速度的提升来自"首字延迟"的缩短，不是总计算量的减少。

④
多轮对话历史全量重发 = 成本快速累积

模型无记忆，上下文历史每轮都要重新送进去。控制成本的核心：截断旧历史 + 结构化输出 + 必要时对 system prompt 启用缓存。

本章词汇表

API
Application Programming Interface（应用程序接口）。两个程序之间通信的约定：调用方按规定格式发请求，服务方按规定格式返回响应。大模型 API 让你用代码驱动模型，而不必自己训练。
HTTP POST
HTTP 协议中用于"提交数据"的请求方法。调用大模型 API 用 POST，因为需要在请求体（body）里携带消息历史和参数。
JSON
JavaScript Object Notation。一种轻量级文本数据格式，用大括号表示对象，中括号表示数组。大模型 API 的请求体和响应体都用 JSON 格式。
Endpoint
API 调用的目标 URL，指向服务器上的特定功能。如 api.deepseek.com/chat/completions 专门处理聊天请求，与图像或音频接口是不同的 endpoint。
API Key
API 服务商发给你的身份凭证（通常以 sk- 开头的长字符串）。每次请求都要带上，服务商据此识别账户、计费、限速。相当于你在该平台的"密码+钱包"组合。
Bearer Token
HTTP 鉴权方案，放在 Authorization 请求头里。"Bearer"意为持有者，服务器不验证你是谁，只验证 token 合法性——谁持有就代表谁。这就是 key 泄露极危险的原因。
SSE（流式输出）
Server-Sent Events，服务器推送事件。HTTP 连接保持打开，服务器持续推送 data 行，每行含一个 token 的增量文本。大模型用它实现"字在蹦出来"的效果，与自回归逐 token 生成天然吻合。
Context Window
模型一次能处理的最大 token 数（输入 + 输出之和）。超出后早期内容被截断，模型会"忘记"对话开头。常见值：32K、128K、200K token。
