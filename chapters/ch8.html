你的助手在自己电脑上能跑——别人怎么用？

在 ch3 到 ch7，你的助手一直在本地跑：python3 ch5-rag-pipeline.py，在终端里回答问题。很好——但产品不是只给自己用的。

想象三个场景
场景 A
同事想用你的 HR 文档助手，但他没装 Python，也没有你的 API key。
场景 B
你的笔记本在开会，但用户的请求还在来——助手挂了。

②

从脚本到服务：你成了 API 的提供方

把 ch5 的 RAG 管线包成 HTTP 接口，只需三件事：

from fastapi import FastAPI
from pydantic import BaseModel
from ch5_rag_pipeline import rag_answer   # 你已有的 RAG 函数

app = FastAPI()

class AskRequest(BaseModel):
    question: str

class AskResponse(BaseModel):
    answer: str
    context_used: list[str]

@app.post("/ask", response_model=AskResponse)
def ask(req: AskRequest):
    answer, ctx = rag_answer(req.question)
    return AskResponse(answer=answer, context_used=ctx)

# uvicorn ch8_fastapi:app --host 0.0.0.0 --port 8000
启动后访问 /docs，FastAPI 自动生成交互式 Swagger 文档，同事可以直接在浏览器里测试接口。

回想 ch4 的架构：你写的代码发出一个 HTTP POST，DeepSeek/Anthropic 的服务器收到请求、跑模型、返回 JSON。你是调用方（client），他们是提供方（server）。

ch4：你 = 调用方
Python 脚本 → POST /chat/completions → DeepSeek
⇄
ch8：你 = 提供方
同事/前端 → POST /ask → 你的 FastAPI

现在你的 FastAPI 服务内部做的事：

①
收到请求

解析 JSON body，验证字段（Pydantic 自动做）。

②
跑业务逻辑

调 ch5 的 RAG 检索 → 拼 prompt → 调 DeepSeek API（你现在是 DeepSeek 的调用方）。

③
返回响应

把答案和上下文序列化成 JSON 返回给调用方。

关键洞察：一个 AI 服务的"全栈"同时扮演两个角色——对上游 LLM API 你是调用方，对下游用户你是提供方。ch4 教的请求格式、鉴权、错误处理，现在全部用在你自己的服务上，角色对称互换。

AI 助手最终需要和其他系统集成——前端、移动 APP、内部工作流工具、Slack Bot……它们用不同语言、不同框架写成。REST API 用 HTTP + JSON，是所有平台都能说的"普通话"。

REST API 的好处
  • 语言无关（任何客户端都能调）
  • 可以独立升级助手后端
  • 可以在不同前端复用同一个 API
  • 容易加鉴权、限流、日志
行业里怎么用
  • OpenAI / DeepSeek 本身也是 REST API
  • 企业内部 AI 平台统一对外暴露 /chat
  • Webhook 也是 REST（模型工具调用回调）
  • LangChain / LlamaIndex 可以直接包成 API
③

跑在哪：三种运行环境

☁ Serverless
代表：Cloudflare Workers、AWS Lambda、Vercel Functions。
按请求计费，0 流量 = 0 费用；自动扩容。
📦 容器（Docker）
代表：Railway、Fly.io、Google Cloud Run。
镜像打包，环境一致，启动比 VM 快。
🖥 VM / 云服务器
代表：AWS EC2、Hetzner、DigitalOcean。
完全控制，持久进程，可挂 GPU。

三种环境的核心差异都来自同一个问题：你的进程在没有请求时是否还在运行？

维度 Serverless 容器 VM
闲时费用 ≈ 0 小（按容器付） 按月付，不管用没用
冷启动延迟 高（百 ms ~ 秒级） 中（数百 ms） 无（进程常驻）
自动扩容 ✓ 内置 ✓ 需配置 手动/另配
持久进程/磁盘 ✗（无状态） 有限 ✓ 完整控制
适合 RAG（向量库常驻） 较难（冷启动重建） ✓ ✓
冷启动本质：Serverless 函数闲置后进程被销毁。下次请求到来时，平台要重新启动进程、加载你的代码和依赖——这段时间就是冷启动延迟。RAG 场景里，向量库也要重新加载进内存，可能额外增加数秒。这是 Serverless 做 RAG 服务的最大挑战。
你的 Cloudflare Worker：它是 Serverless——用来转发 API key，无状态、极轻量，冷启动不是问题。但如果想把向量库也放上去，就要换成容器了。
推荐：Railway / Fly.io（容器）
  • 免费额度够演示用
  • git push 自动部署
  • 支持持久卷（存 Chroma 向量库）
  • 有 HTTPS、自定义域名
入门选 HuggingFace Spaces
  • 零配置，传 Python 文件即可
  • Gradio / Streamlit 前端内置
  • AI 招聘方熟悉这个平台
  • 作品集展示效果好

生产中的密钥：绝不进代码

✗
绝不进代码

不要把 sk-xxx 写死在 Python 文件里，也不要提交到 Git。一旦推上 GitHub（即使立刻删除），密钥就可能被爬虫抓走。

✓
用环境变量

os.environ["DEEPSEEK_API_KEY"]——在云平台的"Environment Variables"面板填入，代码里只读变量名。

✓✓
生产用密钥管理服务

AWS Secrets Manager、HashiCorp Vault、GCP Secret Manager——加密存储、细粒度权限、自动轮换。

# .gitignore 必须有
.env
*.env
secrets/

# 代码里只读环境变量
import os
api_key = os.environ["DEEPSEEK_API_KEY"]   # 正确

在 ch4 你学到：API key 放在 HTTP 请求头 Authorization: Bearer sk-xxx——持有 token 的人就被视为合法用户，服务器不问你是谁。密钥一旦泄露，攻击者可以用你的名义和配额调 API，账单和你无关。

你在 BYOK 方案里也做了同样的事：API key 不进前端 JS（任何人打开 DevTools 就能看），而是存在 sessionStorage 里，通过 Cloudflare Worker 转发——Worker 持有 key，前端不持有 key。这是"密钥不进前端"的实践。

密钥泄露的后果
  • 攻击者消耗你的 API 配额（账单暴增）
  • 访问你的数据（如知识库）
  • 冒充你的服务发出请求
  • GitHub 仓库历史里删掉但已被爬走
正确分层
  • 前端（浏览器）：不持有任何密钥
  • 你的后端 API（FastAPI）：持有上游密钥，通过环境变量注入
  • 用户对你的 API 鉴权：另发一套 key，独立权限
密钥轮换：生产环境每隔一段时间（30~90天）主动更换密钥，即使没有泄露迹象。旧密钥作废，攻击者持有的历史密钥失效。密钥管理服务可以自动完成这个流程。

AI 应用不同于传统应用的一个特殊之处：每次调用都有实际成本（按 token 计费），而不是消耗自己的 CPU。密钥一旦泄露，不是"网站被黑"而是"账单爆炸"——攻击者会自动化地刷你的配额。

实际生产中还需要：对调用你的 API 的用户也做鉴权（否则你的 FastAPI 也成了别人的免费代理）；设置 rate limiting（限制每个用户每分钟的调用次数）；设置预算告警（API 费用超过阈值时自动通知）。

可观测：日志·监控·成本追踪

📋 日志（Logs）
每次请求的入参、出参、耗时、异常。出问题时能回溯"当时发生了什么"。
📊 指标（Metrics）
聚合数值：QPS（每秒请求数）、P95 延迟、错误率、每日 token 消耗、成本。
🔔 告警（Alerts）
错误率 > 5%、延迟 P95 > 5s、日费用 > $50——触发时自动通知（Slack / 邮件）。
# FastAPI 里加最简单的结构化日志
import logging, time, json

@app.post("/ask")
def ask(req: AskRequest):
    t0 = time.time()
    answer, ctx = rag_answer(req.question)
    latency_ms = (time.time() - t0) * 1000
    logging.info(json.dumps({
        "question_len": len(req.question),
        "answer_len": len(answer),
        "latency_ms": round(latency_ms),
        "ctx_count": len(ctx)
    }))
    return AskResponse(answer=answer, context_used=ctx)

📌 回扣 ch7：生产监控就是在线评估

ch7 说到"在线评估"——系统上线后，通过观察真实用户行为来评估质量：用户有没有追问？有没有点"没用"？有没有反复改问法？

📌 回扣 ch4：成本追踪是 token 计费的实战

ch4 你知道了 token 的成本公式：输入 token × 输入价格 + 输出 token × 输出价格。在生产环境里，你需要在每次 API 调用后把 usage.prompt_tokens 和 usage.completion_tokens 写进日志，再按价格折算。这样你能看到"每天花了多少钱"、"哪类问题最贵"、"RAG 检索带来的 token 增量有多少"——是 ch4 知识的直接延伸。

一套典型的 AI 服务监控栈：
日志 → Loki 或 CloudWatch Logs 收集 → Grafana 或 Datadog 可视化 → 告警规则触发 PagerDuty / Slack。
Token 成本追踪：LangSmith（OpenAI/Claude 生态）或自建 PostgreSQL 成本表。

上线不是终点。没有监控的 AI 服务和"扔出去不管"没区别——你不知道它是否还在跑、用户是否满意、是否在漏钱。

AI 应用的 可观测性 比传统应用更重要，因为：LLM 的输出是概率性的（同样输入可能有不同输出），错误不会抛异常（模型会自信地给出错误答案），成本是实时产生的（不监控就不知道有没有滥用）。

面向用户的延迟与流式输出

RAG 答案可能需要几秒生成。用非流式接口，用户等全部完成才看到结果（空白 + 突然全出）；用流式，用户看到文字一个个出现——体验差距巨大。

from fastapi.responses import StreamingResponse

@app.post("/ask/stream")
def ask_stream(req: AskRequest):
    # 先做 RAG 检索（快，毫秒级）
    ctx = retrieve(req.question)

    def generate():
        # 再用流式调大模型
        for chunk in ds.chat.completions.create(
            model="deepseek-chat",
            messages=[{"role":"user","content": build_prompt(ctx, req.question)}],
            stream=True
        ):
            delta = chunk.choices[0].delta.content or ""
            # SSE 格式：data: xxx\n\n
            yield f"data: {delta}\n\n"
        yield "data: [DONE]\n\n"

    return StreamingResponse(generate(), media_type="text/event-stream")
前端用 EventSource 或 fetch + ReadableStream 消费 SSE，每收到一个 data: 行就把 delta 追加到页面——就是这个学习网站里互动演示的实现方式。

ch4 讲过 SSE（Server-Sent Events）——HTTP 连接保持打开，服务器持续向客户端推送 data: 行。当时你是 SSE 的消费方（读取 DeepSeek 推送来的 token）。

现在你的 FastAPI 要实现流式接口，角色同样反转：你成了 SSE 的生产方。逻辑是这样的链条：

用户浏览器
SSE 消费方
→
你的 FastAPI
SSE 生产方
+ DeepSeek 消费方
→
DeepSeek API
SSE 生产方

你的服务做的是"SSE 中继"：从 DeepSeek 收到 chunk，立刻转发给用户浏览器，不在中间缓冲。这样 TTFT（首个 token 到达时间）= RAG 检索时间 + DeepSeek 开始输出第一个 token 的时间，通常在 1-2 秒——用户感知到的延迟大幅降低。

延迟三段：RAG 检索（embedding 计算 + 向量库查询，通常 <200ms）→ LLM 第一个 token 延迟（TTFT，取决于模型和服务商队列）→ 每个后续 token 的间隔（TBT，token between tokens）。流式把 TBT 变成了用户可见的进度，而非等待黑屏。

人类对等待的感知有个门槛：<100ms 感觉瞬时，100ms-1s 感觉流畅，1-3s 明显等待，>3s 开始焦虑，>10s 会放弃。AI 应用的 LLM 调用很难做到 <1s——流式输出是目前最有效的感知延迟优化手段，它不让模型更快，但让用户感觉没那么漫长。

其他降低延迟的方法：缩短 prompt（更少输入 token = 更快处理）、用更小的模型做简单任务、在 RAG 检索和 LLM 调用间做并行（如预热缓存）、选延迟更低的 API 区域部署。

本章小结 · 主轴总结

ch8 核心要点：部署与作品集
  • 你成了 API 提供方：FastAPI 把 RAG+Agent 脚本包成 HTTP 服务。ch4 学的调用技术对称反转——对用户你是提供方，对 DeepSeek 你还是调用方。
  • 跑在哪取决于三角权衡：Serverless（≈0 闲时成本，冷启动高）/ 容器（推荐 RAG 场景）/ VM（完整控制）。你的 Cloudflare Worker 就是 serverless 的实践。
  • 密钥绝不进代码：环境变量注入 → 密钥管理服务 → 定期轮换。前端不持有密钥（你在 BYOK 方案里已经做过这件事）。
  • 可观测性 = 工程视角的在线评估：日志 + 指标 + 告警，持续追踪质量和成本。ch7 的在线评估指标就活在你的监控面板里。
  • 流式输出降低感知延迟：SSE 中继——从 DeepSeek 收到 chunk 立刻转发给浏览器，TTFT 而非 TTLT，用户体验差距巨大。ch4 的 SSE 知识正面用上。
  • 作品集要具体：问题定义 + 架构 + 技术选型理由 + 定量评估结果 + 可运行 demo。简历表述用具体技术栈和数字，不用"熟悉 AI"。

词汇表

部署（Deployment）
把在本地开发好的应用发布到公网可访问的服务器上，让其他人或系统能通过 HTTP 调用。AI 助手的部署通常包括：代码容器化、配置环境变量、接入密钥管理和监控。
API 提供方（API Provider）
对外暴露 HTTP 接口、响应他人请求的一方。在 ch4 你是调用方（调 DeepSeek）；在 ch8 你同时还是提供方（你的 FastAPI 被前端/同事调）。同一个服务可以对上游是调用方、对下游是提供方。
serverless（无服务器）
一种云运行模型：按请求计费，平台自动管理服务器。闲时进程销毁（冷启动问题），有请求时自动启动。代表：Cloudflare Workers、AWS Lambda。适合无状态、轻量的函数，不适合需要常驻内存的 RAG 向量库。
冷启动（Cold Start）
Serverless 函数闲置后进程被销毁，下次请求到来时重新启动进程、加载代码和依赖的过程。延迟可达数百毫秒到数秒。RAG 场景还需要重新加载向量库，冷启动更长。
容器（Container）
Docker 等工具将应用代码、依赖、配置打包成可移植单元。在任何安装了 Docker 的机器上运行效果一致。部署 RAG 服务的推荐形态：进程常驻、支持持久卷、启动比 VM 快。
环境变量（Environment Variable）
操作系统级别的键值对，代码通过 os.environ["KEY"] 读取。用于传入 API key、数据库地址等配置，不写进代码文件，不进 Git 仓库。云平台在部署时注入，是密钥安全的第一道防线。
密钥管理（Secret Management）
加密存储、细粒度权限控制、自动轮换 API key 等敏感凭据的服务（AWS Secrets Manager、HashiCorp Vault）。比环境变量更安全：访问有日志、权限可撤销、密钥可自动轮换，适合生产环境。
可观测性（Observability）
通过日志（Logs）、指标（Metrics）、追踪（Traces）三类数据，使系统内部状态从外部可被理解和调试的工程能力。AI 服务的可观测性额外包括质量指标（答案满意度）和成本指标（每日 token 消耗）。
FastAPI
Python 的高性能异步 Web 框架，自动从函数类型注解生成 OpenAPI 文档（/docs）。把 Python 函数包成 HTTP 接口只需几行代码，是 AI 助手后端部署的常见选择。
作品集（Portfolio）
展示你技术能力的项目集合。AI 方向的作品集核心：能独立完成从问题定义→数据/知识库→模型/提示词→评估→部署的完整链条，并有可运行的 demo 和量化结果，而不只是学了哪些知识。
